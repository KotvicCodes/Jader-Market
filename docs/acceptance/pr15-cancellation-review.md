## Confirmed findings and corrections

1. **P2 — cancelled recovery could leave a Docker container behind while deleting its credentials.** `restore()` set `created = true` only after the Docker client returned successfully. If Docker accepted creation and the client was then interrupted, the helper rejected and cleanup skipped the container. A regression exercising the real CLI with a substituted Docker executable reproduced the orphan and missing private directory. Failed restores now query only their exact random container name and ownership label, including when creation did not return successfully, and remove the owned container before deleting credentials. A private `pending-restore.json` records its identity before creation. If Docker cleanup fails, the directory and credentials remain available for the operator, while decrypted staging is deleted. The regressions verify both successful cleanup and identity preservation on cleanup failure.

2. **P2 — recovery swallowed cancellation during readiness retries.** The subprocess helper's SIGTERM rejection was caught as an ordinary readiness failure; the CLI kept retrying instead of stopping. Also, signal handlers existed only while a subprocess was active. The readiness regression observed the original CLI still running after cancellation. Backup/recovery now retains one cancellation signal for the entire operation; active subprocesses stop, later subprocesses reject before starting, readiness retries propagate cancellation, and cleanup uses independent commands. A subprocess regression verifies cancellation across consecutive commands. The normal deadlines and financial acceptance thresholds are unchanged.

Both original cancellation regressions failed before the implementation change and passed afterward. No additional financial business-logic defect was reproduced in the reviewed changes or exercised workflows. These results do not establish correctness for every input or deployment.
