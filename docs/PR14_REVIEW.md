The three findings below are corrected in the follow-up review commit on this pull request.

1. **P1: successful backups could contain the wrong authentication key, release identity or source database.** The original backup inspected the Compose database and resolved `JADER_IMAGE`, but never compared the environment file with the deployed app. A stale yet well-formed `AUTH_SECRET` was encrypted into the archive and a reused image tag was recorded as if it described the running release. An app configured against another database could also be backed up from the local Compose database. Replication and freshness could succeed despite these mismatches. Backup now requires the app container and checks all existing app/worker/monitor containers against the configured image ID, key and canonical Compose database URL before dumping. Stopped containers remain valid for fenced upgrades. Six mismatch regression cases fail against the original PR and pass with the fix; the real Docker drill also rejects a wrong source key and retagged source image.

2. **P2: recovery unnecessarily depended on a mutable image tag.** The original restore inspected the recorded tag before checking the immutable ID. Reusing or deleting that tag prevented recovery even when the exact archived image was still present. The original Docker drill fails at restore after deliberately moving the tag. Restore now inspects and runs the recorded immutable ID; the tag is informational. The expanded drill restores successfully after moving the tag and verifies the restored state with the original artifact. Missing immutable images still fail before database creation.

3. **P2: PostgreSQL error details could disclose restored private values through container logs.** Suppressing SQL statements and subprocess stderr does not suppress server error details. A duplicate-key probe using the original restore settings logged a synthetic private value. Restore now also sets `log_min_messages=panic`, matching the production deployment's logging policy. The expanded drill deliberately triggers a duplicate-key error and checks both Docker stdout and stderr for the private sentinel; it is absent.

Dump failure handling is also tightened: encryption and the producer are both settled before deleting the partial file or releasing the backup lock. The CLI regression verifies that a failed producer publishes nothing, leaves no lock/partial, and permits a subsequent successful backup. The original implementation also passed this particular failure fixture; this change closes the cleanup ordering race identified by inspection.
